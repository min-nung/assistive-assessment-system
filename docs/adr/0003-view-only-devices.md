# 唯讀檢視裝置：以「不上傳」取代「不能編輯」

## 背景

實際使用形態是一台裝置記錄、另一台裝置閱覽：治療師帶手機到案家做評估，回到辦公室用電腦調閱同一批紀錄。

但雲端備份的設計預設每台裝置都是會寫入的裝置（見 [0001](./0001-google-drive-backup-not-sync.md)）。電腦端連結同一個 Google 帳號後，就成為另一台有權覆蓋那份唯一快照的裝置。危險不在第一次開啟——那時本機沒有資料，[0002](./0002-user-resolves-conflicts.md) 的衝突閘門也還擋得住——而在使用者被問到衝突時選了「保留本機」，或是在採用雲端資料之後又在電腦上動了什麼：此後電腦的 `lastUploadedAt` 已與雲端對齊，它會像任何一台正常裝置一樣，把手上這份（可能已經過時的）副本自動送上去。

換句話說，一台只是用來「看」的裝置，仍隨時可能安靜地覆蓋掉真正在做評估的那台裝置的備份。

## 決定

新增**唯讀檢視裝置**：由每台裝置各自持有的一個設定，開啟後這台裝置永不上傳。

判斷放在 `sync-decision.js`——唯讀的優先順序高於衝突、離線與 debounce，僅次於「尚未連結」。這使「唯讀即不上傳」成為決策本身的性質，而不是每個呼叫端各自要記得的事。`cloud-backup.js` 在真正發出網路請求前再擋一次，且刻意擋在 `forceUpload` 之上——`forceUpload` 存在的目的正是繞過決策閘門。

**唯讀不等於不能編輯。** 表單照常可以輸入，只是第一次修改時會提醒「這項修改只會留在本機」。

可用 `?readonly=1` 開啟並記住，讓電腦端直接把這個網址存成書籤。

## 理由

會造成資料遺失的是**上傳**，不是編輯。把「不能上傳」寫進決策層，是一句可以被測試、也可以被證明的全稱敘述：`tests/sync-decision.test.js` 直接斷言唯讀情境下不存在任何回傳 `upload` 的組合。反過來，若改以停用表單來達成，保護就散落在每一個輸入元件上，任何新增的表單都可能漏掉，而且漏掉時沒有任何跡象。

不鎖住表單還有一個臨床上的理由：治療師可能就是想在電腦上先把想到的東西記下來。鎖住會讓應用程式看起來壞了，而不是看起來安全。

唯讀裝置不再詢問衝突。衝突之所以是個問題，是因為這台裝置可能覆蓋雲端；既然它不會，「雲端比較新」就不是異常，而是它每次開啟時本來就預期看到的狀態，也正是它要讀的東西。若仍然詢問，唯一的作用是提供一個覆蓋雲端的按鈕——正是本決定要消除的東西。

## 後果

唯讀裝置上的修改沒有任何備份。這是刻意的：那些修改依定義不屬於真相來源。載入雲端資料會覆蓋它們，只有在本機確實存在載入後才產生的修改時，才會先自動匯出一份保險。

唯讀裝置不再顯示 7 天手動備份提醒，也不再顯示雲端備份過久未上傳的提醒——它手上沒有任何原創資料值得提醒。

解除唯讀是較危險的方向：一台讀了好幾週快照的裝置可能持有過時副本，解除後它就恢復寫入權。因此解除時會重跑一次啟動衝突檢查，把它交還給 [0002](./0002-user-resolves-conflicts.md) 的既有流程處理。
