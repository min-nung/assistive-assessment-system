# 個案評估資料雲端備份

**標籤**：`ready-for-agent`

## Problem Statement

治療師在案家或機構完成的個案評估資料，目前只存在瀏覽器的 localStorage 裡。這代表：

- 清除瀏覽器資料、更換裝置、手機或平板損壞遺失，評估資料就永久消失
- 唯一的保護手段是手動匯出 JSON 備份，而系統每 7 天才提醒一次，經常被忽略
- 就算記得匯出，那個 JSON 檔案還是存在同一台裝置上——裝置壞了，備份也一起沒了

對臨床工作而言這個風險太高。一份輔具評估包含身體尺寸測量、壓傷狀態、關節活動度等需要當面接觸個案才能取得的資料，遺失後無法重建，只能請個案再跑一趟。

治療師需要的是「我不用想這件事，資料就自動安全了」。

## Solution

個案資料自動備份到治療師自己的 Google Drive。

治療師連結一次 Google 帳號之後，每次評估資料變動，系統會在他停止操作數秒後自動把完整快照上傳到他自己的雲端硬碟。更換裝置時，登入同一個 Google 帳號即可把資料取回。

這是**備份**，不是同步——localStorage 仍是唯一真相來源，雲端資料只在使用者明確選擇時才會取代本機資料。詳見 [ADR 0001](../../docs/adr/0001-google-drive-backup-not-sync.md)。

三個不可妥協的原則：

1. **絕不阻擋離線使用。** 案家常常沒有網路。未登入、離線、授權過期，應用程式的所有評估功能都必須照常運作。
2. **絕不靜默覆蓋資料。** 偵測到雲端快照較新時，一律停下來問使用者，不自動合併。詳見 [ADR 0002](../../docs/adr/0002-user-resolves-conflicts.md)。
3. **備份狀態必須誠實可見。** 使用者必須隨時能看出現在到底有沒有在備份。最糟的失敗是他以為有備份而不再手動匯出，結果兩邊都沒有。

## User Stories

### 連結與授權

1. 身為治療師，我想在設定選單中看到「雲端備份」入口，讓我知道這個功能存在。
2. 身為治療師，我想在未連結時看到明確的「未連結」狀態與一個連結按鈕，讓我知道目前資料還沒有雲端保護。
3. 身為治療師，我想在點下連結按鈕後看到 Google 的授權畫面，讓我確認自己授權了什麼。
4. 身為治療師，我想在授權畫面上看到系統只要求存取「這個應用程式建立的檔案」，讓我放心它不會讀取我雲端硬碟裡的其他資料。
5. 身為治療師，我想在授權完成後立刻看到狀態變成「已連結」，讓我確認連結成功。
6. 身為治療師，我想在下次開啟應用程式時不必重新登入，讓我不用每天處理授權。
7. 身為治療師，我想在授權過期時看到狀態變成「需要重新連結」，讓我知道備份已經停了。
8. 身為治療師，我想在授權過期時不被強制彈窗打斷正在進行的評估，讓我能先完成手上的工作。
9. 身為治療師，我想能主動解除 Google 帳號連結，讓我在共用裝置上能保護自己的資料。
10. 身為治療師，我想在解除連結後，雲端上既有的快照不會被自動刪除，讓我不會因為誤觸而失去備份。

### 自動上傳

11. 身為治療師，我想在填寫評估表單時不必按任何儲存或上傳按鈕，讓我專注在個案身上而不是操作介面。
12. 身為治療師，我想在連續打字時不要每個字都觸發上傳，讓我不浪費行動網路流量與電力。
13. 身為治療師，我想在停止操作幾秒後資料就自動上傳，讓我隨時離開都不會失去進度。
14. 身為治療師，我想在切換到其他應用程式或鎖上螢幕時，尚未上傳的變動會立刻被送出，讓我不會因為隨手關掉而掉資料。
15. 身為治療師，我想在上傳進行中看到不干擾的提示，讓我知道系統正在工作。
16. 身為治療師，我想在上傳成功後看到「雲端：剛剛」之類的時間標示，讓我確認資料真的上去了。
17. 身為治療師，我想在新增、刪除、重新命名個案後也會觸發上傳，讓所有變更都被保護，而不只是表單欄位。

### 離線與失敗

18. 身為治療師，我想在沒有網路的案家照常進行完整評估，讓我不會因為訊號問題而無法工作。
19. 身為治療師，我想在離線時看到「離線，待恢復連線後上傳」的狀態，讓我知道資料暫時只在本機。
20. 身為治療師，我想在恢復連線後系統自動補傳，讓我不必記得回頭做這件事。
21. 身為治療師，我想在上傳失敗時看到失敗狀態而不是假裝成功，讓我能決定要不要手動匯出 JSON 作為保險。
22. 身為治療師，我想在上傳失敗後系統會自動重試，讓暫時性的網路問題不需要我介入。
23. 身為治療師，我想在雲端備份完全無法運作時，仍然能使用原本的手動 JSON 匯出功能，讓我永遠有一條退路。

### 取回與衝突

24. 身為治療師，我想在新裝置上登入 Google 帳號後，看到系統提示雲端有可載入的備份，讓我能把資料取回。
25. 身為治療師，我想在載入雲端快照前看到它的時間與個案數量，讓我確認要載入的是正確的版本。
26. 身為治療師，我想在載入雲端快照前必須明確確認，讓我不會意外覆蓋本機資料。
27. 身為治療師，我想在雲端快照比本機新時得到提示，讓我不會不小心用舊資料覆蓋掉新的評估成果。
28. 身為治療師，我想在發生衝突時清楚看到兩份快照各自的時間與個案數量，讓我有依據做選擇。
29. 身為治療師，我想在衝突時能選擇保留本機或採用雲端，讓決定權在我手上。
30. 身為治療師，我想在衝突時能選擇「先不要決定」並繼續工作，讓我不會被迫在案家當場處理這件事。
31. 身為治療師，我想在尚未解決衝突前系統不會自動上傳，讓我的猶豫不會導致資料被覆蓋。
32. 身為治療師，我想在載入雲端快照前，本機資料會先被自動匯出成 JSON 檔，讓我萬一選錯還有救。

### 狀態可見性

33. 身為治療師，我想在既有的資料備份面板中同時看到手動備份與雲端備份的狀態，讓我在同一個地方掌握全部資訊。
34. 身為治療師，我想在雲端備份正常運作時，不再被 7 天一次的手動備份提醒打擾，讓提醒保留給真正需要注意的時候。
35. 身為治療師，我想在雲端備份停止運作超過一段時間時收到提醒，讓我不會在毫無察覺的狀況下失去保護。

## Implementation Decisions

### 模組結構

新增 `cloud/` 目錄，內含三個職責分明的模組：

**`cloud/sync-decision.js` — 決策模組（純函式）**

這是整個功能的核心，也是唯一有自動化測試的模組。它不碰網路、不碰 DOM、不碰 localStorage、不碰時間。

介面只有一個函式：接收一份描述當下情境的純資料物件，回傳一個描述「下一步該做什麼」的純資料物件。

輸入包含：是否已連結、是否在線、本機最後變動時間、本機最後成功上傳時間、雲端快照時間、距離最後一次變動經過多久、是否有未解決的衝突、觸發原因（定時檢查／使用者離開頁面／應用程式啟動）。

輸出為以下決定之一：
- `idle` — 什麼都不做
- `upload` — 立刻上傳
- `wait` — 尚在 debounce 期間，稍後再問
- `conflict` — 雲端較新，須詢問使用者
- `needs-auth` — 需要重新授權
- `offline` — 離線，暫緩

所有可能導致資料遺失的判斷都集中在這裡。

**`cloud/drive-client.js` — 執行模組**

負責 Google Identity Services 與 Drive API 的實際呼叫：取得 token、搜尋既有快照檔、上傳、下載。刻意做薄——不含任何「該不該做」的判斷，只負責「照著做」。

**`cloud/cloud-backup.js` — 協調模組**

串接決策與執行：監聽變動、管理 debounce 計時器、監聽 `visibilitychange` 與 `online`／`offline`、呼叫決策模組、依決定驅動執行模組、更新 UI 狀態。

### 與既有程式碼的整合點

**變動通知**：`core/state.js` 的 `saveState()` 是所有資料變動的匯流點，每次個案資料改變都會經過它。在此加入一個可註冊的變動回呼，讓雲端模組能得知「有東西變了」。此為單一整合點——不需要修改任何表單模組。

**快照格式**：直接沿用 `backup/backup.js` 的 `exportBackup()` 既有格式 `{ app, version, exportedAt, cases }`，不新增格式。上傳與下載的都是同一種快照。

**下載驗證**：從 Drive 取回的快照必須經過 `backup/schema.js` 的 `validateBackupPayload()`，與匯入 JSON 檔案採用完全相同的驗證。雲端資料視為不可信輸入。

**套用快照**：沿用 `persistCases()` 與 `migrateCases()`，與既有的匯入還原流程一致，確保舊版快照能被正確升級。

**UI**：擴充既有的 `settingsDialog` 選單與 `backupPanel` 面板，不新增獨立介面。狀態文字沿用 `showToast()` 呈現非阻斷提示。

### 關鍵行為決策

**debounce 5 秒**：最後一次變動後靜候 5 秒才上傳。期間有新變動則重新計時。

**離開時強制送出**：`visibilitychange` 轉為 hidden 時，跳過 debounce 立即上傳，補足「改完馬上關掉」的空窗。

**衝突偵測兩道關卡**：應用程式啟動時比對一次；每次上傳前再比對一次。任一關卡發現雲端較新即進入 `conflict` 狀態並暫停自動上傳。

**單一檔案快照**：Drive 上只維護一個檔案，內含全部個案。以固定檔名搜尋既有檔案再更新，避免瀏覽器資料被清除後產生重複檔案。

**OAuth scope 為 `drive.file`**：只能存取本應用程式建立的檔案。Client ID 為公開資訊，寫入前端設定模組並附註說明；Client Secret 絕不進入前端或版本庫。

**載入雲端前先自動匯出本機**：套用雲端快照會覆蓋本機資料，此為不可逆操作，因此先觸發一次本機 JSON 匯出作為保險。

**失敗重試**：採用指數退避重試，並設上限。持續失敗則進入明確的失敗狀態，不無限重試。

### 部署前置條件

GitHub Pages 必須啟用，因為 OAuth 授權來源需要固定網域。入口檔案 `index_3.html` 需處理為 `index.html`，使網址不含檔名。

## Testing Decisions

### 測試框架

使用 Node 內建的 `node:test` 與 `node:assert`，透過一個 `package.json` 的 test script 執行。不引入任何第三方測試框架。

此選擇刻意維持本專案「零依賴、零建置流程」的既有紀律。決策模組是純函式、無 DOM、無網路，Vitest 等框架提供的瀏覽器環境模擬與 mock 能力在此完全用不到。

### 好的測試長什麼樣

只測試外部行為，不測試實作細節。對決策模組而言，這代表：給一組情境，斷言回傳的決定。測試絕不應該知道模組內部如何比較時間或如何組織條件判斷——只知道「離線時應該回傳 offline」。

測試應以情境命名，讀起來像規格：「雲端快照比本機新時，回傳 conflict 而非 upload」。

### 測試範圍

**`cloud/sync-decision.js` — 完整覆蓋。** 這是唯一被自動化測試的模組。必須涵蓋的情境包括：

- 未連結時回傳 `needs-auth`，且絕不回傳 `upload`
- 離線時回傳 `offline`，且絕不回傳 `upload`
- debounce 未滿 5 秒時回傳 `wait`
- debounce 已滿時回傳 `upload`
- 觸發原因為「使用者離開頁面」時，即使未滿 5 秒也回傳 `upload`
- 雲端快照比本機最後上傳新時回傳 `conflict`
- 有未解決衝突時，任何情況都不回傳 `upload`
- 雲端無快照且本機有資料時回傳 `upload`
- 本機無任何變動時回傳 `idle`
- 應用程式啟動時，雲端較新則回傳 `conflict`

邊界情境同樣必須覆蓋：時間戳相同、時間戳缺失、雲端檔案不存在。

**其他模組——手動驗證。** `drive-client.js` 與 `cloud-backup.js` 涉及真實 OAuth 與網路，為其撰寫的測試只會是在測 mock，不會測到真實失敗。改以手動驗證清單確認，清單需涵蓋：離線填寫評估、切換裝置取回、授權過期、上傳失敗、衝突處理。

### 既有慣例

本專案目前沒有任何測試，這是第一組。`backup/schema.js` 的驗證邏輯是本專案既有的「純函式、易測試」典範，新的決策模組應遵循同樣的風格：無副作用、輸入輸出明確、錯誤訊息清楚。

## Out of Scope

以下項目明確排除，且部分為刻意的架構決定，不應在實作時「順手加上」：

- **多裝置即時同步。** Google Drive 無推播機制，做不到。詳見 ADR 0001。
- **自動合併衝突。** 在現有資料模型下沒有安全的定義，需要完整 CRDT。詳見 ADR 0002。
- **跨治療師共享個案。** 需要真正的後端與權限模型。
- **強制登入。** 會摧毀離線優先的核心價值。
- **移除既有的手動 JSON 匯出／匯入。** 雲端備份是增加一層保險，不是取代。使用者必須永遠能把資料拿在手上。
- **快照版本歷史。** Drive 上只維護一份最新快照，不保留歷史版本。
- **個案層級的選擇性同步。** 快照永遠是全部個案，不提供部分上傳。
- **Google 應用程式驗證審查。** 使用者數在 100 人以內時維持測試模式即可。
- **其他雲端供應商。** 不做 Dropbox、OneDrive 或 iCloud。

## Further Notes
